# 0. RÈGLE ABSOLUE — CONTEXTE DU PROJET

Tu travailles sur le projet AQCS CYCLOPS.

Tu dois TOUJOURS conserver le contexte global du projet avant de modifier du code.

Ne transforme jamais le projet en une simple application chatbot.

CYCLOPS est un assistant technique industriel destiné à accompagner les activités d'inspection.

Le projet combine :

- procédures techniques
- NDT
- APL
- APE
- APVG
- recherche locale
- assistant IA
- animations / visualisations 3D
- interface bilingue FR/EN
- authentification
- aide contextuelle selon la méthode d'inspection

Les méthodes actuellement représentées sont :

- PT — Penetrant Testing
- MT — Magnetic Testing
- UT — Ultrasonic Testing
- RT — Radiographic Testing
- VT — Visual Testing
- APL — Appareils / équipements de levage
- APE — Appareils / équipements électriques
- APVG — Appareils / équipements sous pression
- OTHER

---

# 1. OBJECTIF FINAL

Construire une plateforme AQCS CYCLOPS professionnelle permettant à un inspecteur de :

1. sélectionner ou identifier une méthode d'inspection ;
2. consulter rapidement la procédure correspondante ;
3. comprendre les étapes de contrôle ;
4. consulter les références/codes disponibles ;
5. visualiser une représentation animée de la méthode ;
6. rechercher localement dans la base de connaissances ;
7. poser une question à l'assistant IA ;
8. recevoir une réponse contextualisée par rapport à la méthode ;
9. identifier les sources utilisées ;
10. distinguer clairement :
   - procédure AQCS
   - référence normative
   - information générale
   - réponse générée par IA ;
11. fonctionner autant que possible même lorsque l'API IA est indisponible.

# 6. RÈGLE IMPORTANTE POUR L'IA

L'assistant ne doit jamais inventer une exigence normative.

Il doit distinguer :

### SOURCE AQCS

Information provenant des procédures internes AQCS.

### NORME / CODE

Information provenant d'un code ou standard identifié.

### INFORMATION GÉNÉRALE

Connaissance générale qui n'est pas présentée comme une exigence AQCS.

### IA

Interprétation ou explication générée.

---

# 7. COMPORTEMENT ATTENDU DE L'IA

Exemple :

Utilisateur :

"J'ai une indication UT de 42 mm, +6 dB et longueur 8 mm."

L'IA ne doit pas immédiatement dire :

"Accepté"

ou

"Rejeté".

Elle doit vérifier le contexte disponible.

Elle peut demander :

- épaisseur
- matériau
- type de soudure
- code applicable
- édition du code
- niveau d'acceptation
- procédure applicable
- localisation de l'indication
- autres informations nécessaires

Puis expliquer ce qui peut être déterminé avec les données disponibles.

# 9. LOCAL SEARCH

Le projet possède déjà une recherche locale basée sur les mots-clés.

Cette recherche doit être conservée comme fallback.

Objectif futur :

Recherche hybride :

Keyword Search
+
Semantic Search
+
Method Detection

Exemple :

"Comment contrôler une soudure avec UT ?"

Le système doit détecter :

method = UT

Puis rechercher principalement dans :

PROC.UT

et les documents associés.

# 10. 3D / VISUALISATION

Les méthodes disposent de représentations animées.

Pour chaque méthode :

1. équipement ;
2. pièce contrôlée ;
3. positionnement ;
4. mouvement de l'opérateur ;
5. zone inspectée ;
6. résultat / indication ;
7. légendes ;
8. étapes ;
9. contrôles utilisateur.

L'utilisateur doit pouvoir :

- Play
- Pause
- Reset
- Rotation
- Zoom
- Changer d'étape
- Voir les explications
- Éventuellement écouter une explication vocale

# 13. ASSISTANT IA — INTERFACE

L'assistant doit être accessible depuis toutes les pages pertinentes.

Il doit connaître automatiquement :

- langue
- méthode sélectionnée
- page actuelle
- sujet courant
- contexte utilisateur
- résultats de recherche pertinents

Exemple :

Utilisateur consulte UT.

Il ouvre l'assistant.

Il demande :

"Quel couplant utiliser ?"

Le contexte envoyé doit indiquer :

method = UT

afin que l'IA n'ait pas besoin de deviner le domaine.

P0 = Bloquant / sécurité / erreur critique

# 19. RÈGLE ANTI-RÉGRESSION

AVANT chaque modification :

1. comprendre le code existant ;
2. identifier les dépendances ;
3. identifier ce qui peut être cassé ;
4. modifier le minimum nécessaire ;
5. tester ;
6. vérifier les fonctions existantes.

Ne jamais supprimer une fonctionnalité simplement parce qu'elle semble inutile.

---

# 20. RÈGLE POUR CLAUDE CODE

Lorsque je te demande une modification :

NE FAIS PAS immédiatement du code.

Commence par :

1. scanner les fichiers concernés ;
2. comprendre leur rôle ;
3. identifier les dépendances ;
4. expliquer brièvement le problème ;
5. proposer la modification ;
6. effectuer la modification ;
7. vérifier les erreurs ;
8. résumer les fichiers modifiés.

Si une information est ambiguë :

pose une question avant une modification destructive.
